1 · Overview

SENTINEL is an end-to-end system that turns raw SAR satellite imagery into investigation-ready oil-spill case files. It ingests Sentinel-1 SAR, ocean forcing (ERA5 winds, CMEMS / GLORYS12 currents, optional GFS), and AIS vessel tracks; detects dark slicks; back-tracks them to a likely release point with Lagrangian drift; attributes the spill to suspect vessels; and produces an LLM-written narrative with chain-of-custody hashing.

The system is built as a FastAPI microservice mesh behind a single API gateway, a React/Three.js globe UI, and a shared core library (sentinel_core/). A separate, runtime-switchable training harness (scripts/train.py + ml/) trains the segmentation model, either against the real archive read in place off an external disk or against a statistically-matched synthetic set.

Read this first — the architecture as built vs. as documented. The README's mermaid diagram is aspirational. The code diverges in ways that matter for anyone operating or extending the system, and this document describes the actual code:
  • sentinel_core is not imported by any service — each service re-implements its own loguru + os.getenv config (a real duplication debt, see §9).
  • detect ships two entry points: app.main:app (UNet++, needs torch + a checkpoint) and app.main_det:app (torch-free Tier-A deterministic operator). The lightweight profile runs main_det on 8002 — there is no trained model deployed.
  • attribute and intel are reached only via the Celery worker (tasks.py HTTP fan-out), not by a REST proxy in the gateway.
  • The gateway keeps a legacy in-memory cases dict for /api/v1/cases; only /api/v1/scenes/persist is durable.
Python 3.11 / 3.12 deploy, 3.13 dev FastAPI + httpx + asyncpg UNet++ + SCSE (Tier-B, untrained) Deterministic Lee–Solberg (Tier-A, deployed) OpenDrift / OpenOil PostgreSQL + PostGIS / Redis React + Three.js globe Apple M2, CPU/MPS, no CUDA

3 · Module Responsibilities

3.1 Shared core — sentinel_core/

Despite its name, no service imports this package (see §9). It is the canonical reference implementation of config, logging, errors, provenance and the data-source resolver, and it is used directly by the training harness. Its intended contract:

ModuleResponsibility
config.pySingle pydantic-settings Settings (prefix SENTINEL_, __ nested). Embeds PathSettings, DataSourceSettings, TrainingSettings, LoggingSettings. Key switches: data_source (real|synthetic), scene_grouping (per_file|grid|footprint), image_size (÷32), epochs, test_fraction.

provenance.pyDataProvenance enum (real | synthetic_mock | unavailable | no_real_coverage) and the supports_scientific_claim gate. Synthetic metrics are explicitly "not evidence."
raster.pyGDAL I/O with GDAL_DISABLE_READDIR_ON_OPEN=EMPTY_DIR (≈150× header-scan speedup); header_info() reads bands/CRS/bounds without pixels.

4 · Module Interaction Topology

Inter-service calls follow one rule from AGENTS.md: each service owns one domain; cross-service calls go through the gateway. In practice the gateway is the only node that talks to siblings — and only detect/drift/attribute are REST-proxied; attribute and intel are invoked by the Celery worker fanning out over HTTP. Leaf services never call each other; drift accepts a vessel list in its request body rather than querying ingest.

Two paths through the system.
  • Synchronous per-stage API — a client posts a SAR scene to the gateway, which proxies to detect directly; drift/attribute are proxied too (drift via a circuit-breaker). Good for interactive single-stage calls.
  • Asynchronous full pipeline — POST /api/v1/pipeline/trigger enqueues a Celery task that fans out over HTTP to detect → drift → attribute → intel in order, each stage consuming the previous stage's output. This is how a complete case file is produced.

5 · End-to-End Data Flow (Input → Output)

From a raw SAR GeoTIFF to a citable case file. Each stage is tagged with its provenance and uncertainty posture so the next stage — and the analyst — cannot mistake a flag for a fact.

5.1 What each stage emits

  • detect → GeoJSON polygons (EPSG:4326) + per-blob metrics (area, compactness, elongation, mean dB, contrast) + a Wilson 95% CI per polygon + a per-pixel evidence map. Not a trained model in production (Tier-B is untrained and emits probabilities: null).
  • drift → an inferred origin: center lon/lat, PCA 2σ ellipse (semi_major/semi_minor_km) and non-parametric p50/p95_radius_km, particle count, and a stated note on the WMC ∇·K correction (a no-op here because K is spatially constant — reported, not faked).
  • attribute → ranked suspect vessels with K_ij composite score and Wilson CI. With no real AIS coverage the API returns an empty ranking with a reason — it never fabricates suspects.
  • intel → an LLM-written narrative + legal PDF case file + chain-of-custody hash. With no model available it falls back to a deterministic template and labels it as such.

5.2 Provenance is carried end-to-end

Every datum carries a provenance tag (REAL / SYNTHETIC / UNAVAILABLE / FAILED) and every uncertainty carries a confidence interval, never a lone point estimate. This is the project's core design principle: the system reports what it does not know.

6 · Training & Data-Source Pipeline

The trainer is runtime-switchable between the real archive and a synthetic set; both read in place (nothing is copied to the local machine). The leak-free footprint grouping is what makes the evaluation trustworthy.

Why the training numbers are what they are. The same 10-epoch budget, two splits:
  • per_file split → val IoU 0.8050 — leaked; tiles from one acquisition landed on both sides. ~63% of that number was leakage.
  • footprint split → val IoU 0.2981 — leak-free but still only 8 acquisitions, val-selected.
  • footprint + held-out test → test IoU 0.1447 — the number to quote. On unseen acquisitions the model over-predicts (precision 0.15, recall 0.76): 333k false-positive pixels vs 59k true. No trained model is deployed.

7 · Setup, Dependencies & Configuration

7.1 Runtime & interpreter

  • One managed venv targeted by pyproject.toml; deployment images are Python 3.11 (detect, drift) / 3.12 (api); mypy type-checks under 3.13 (see comment in pyproject.toml for why).
  • Apple M2, no CUDA; MPS used for torch where available. Docker is not installed on the build machine — compose config validates but images are unbuilt (B1/B10).

7.2 Dependencies

Two deliberately separate lists (so the serving image and the trainer aren't pinned to something nobody ran):

  • ML / training (ml/requirements.txt, verified set): torch>=2.2, torchvision>=0.17, timm>=1.0, numpy>=1.26, scipy>=1.11, rasterio>=1.3, pydantic>=2.7, pydantic-settings>=2.3, loguru, python-dotenv.
  • Services: fastapi, httpx, pydantic v2, asyncpg, celery + Redis broker, plus per-service domain libs: opendrift 1.14.11 & cfgrib & xarray & netCDF4 (drift), copernicusmarine 2.4.1 (ingest), rasterio/shapely/scikit-image (detect Tier-A).
  • Frontend: Node + React 18, Three.js/deck.gl, Tailwind, zustand, vitest. strict, no any.

8 · Key Capabilities & Features

Scientific honesty (the headline differentiator)

  • Every metric carries a provenance tag and a confidence interval — never a lone point estimate.
  • Limitations are registered, not buried (docs/LIMITATIONS.md, 40+ entries).
  • The deployed detector is reproducible and explainable (no weights, no black box).

Leak-free evaluation engineering

  • Footprint scene grouping (union-find over tile ground) removes near-duplicate ground; the scene_leakage guard can actually fail now.
  • Real archive read in place — proven by SHA-256 either side of a 10-epoch run; zero bytes copied.
  • Atomic checkpoints; --resume restores the checkpoint's own best val.

Deterministic detection verified on real data

  • On the Wakashio 10 Aug peak: 3.347 km² slick at −9.79 dB, confidence 0.934, Wilson CI [0.902, 0.956] — a textbook SAR signature, corroborated against published imagery.
  • Tiled inference with halo merging; out-of-distribution scenes are flagged, not silently scored.

Modular, domain-isolated services

  • Clean gateway/leaf topology; single responsibility per service; Celery async pipeline.
  • Dual case-store backend (Postgres + durable JSON fallback) that reports which one served a write.
  • Runtime data-source switch (--data-source) with no local copying.

Reproducible dev tooling

  • make test/lint/format/typecheck all clean; 302 tests (115 services + 112 ml + 75 core).
  • Synthetic generator matches the real distribution on 26/28 checks via match_report.json.

9 · Limitations & Technical Debt

9.1 Scientific limitations (the answer may be wrong)

IDLimitationWhy it matters
A1No trained model is deployed. Tier-B UNet++ was trained 3× (10 ep each) but is untrained in prod and emits no probabilities. Quote test IoU 0.1447 if forced."Trained" ≠ "usable"; the model over-predicts on unseen acquisitions.
A2The Wilson CI is not P(oil). It answers "how consistent is the dark-pixel evidence?" not "how likely is this oil?"The most dangerous number — it looks like a probability. Never present it as one.
A3Look-alike filtering needs wind. Without 2–10 m/s wind, rain/low-wind/biogenic films can pass.Detections emitted but flagged LOW_CONFIDENCE_NO_WIND.
A5Backtracking assumes a point-source release and stationary current — false for a wreck leaking over days (the Wakashio case).Inferred origin is plausible, not the origin.
A7Attribution weights are chosen, not fitted (0.6/0.4).K_ij is a structured opinion with a stated interval, not a calibrated probability.
A9The 2020 case cannot be AIS-attributed at all (no free historical Indian-Ocean feed).System honestly renders "satellite-AIS subscription required."
A10Synthetic match misses 2 pooled p99.9 tails; the reference value shifts ±3.5 dB with sample size.Treat those two checks as unresolved, not as evidence.
B12SAR band order is assumed (VH,VV) not measured. Training unaffected; physical "VV" readings unverified.Relabelling would invalidate every index/checkpoint/match report.

9.2 Operational limitations (right answer, can't deliver here)

  • B1 / B10 — Full compose stack and Dockerfile.train have never been built (no Docker daemon). Only config is validated.
  • B2 — Drift container lacks libeccodes0; verified drift numbers came from native macOS. The arm64 image would fail on ERA5 GRIB.
  • B4 — Ollama not running; intel LLM narratives are inert (deterministic template fallback).
  • B5 — Postgres path is written but unexercised; only the JSON fallback store is tested (restart round-trip verified).
  • B6 — Legacy /api/v1/cases CRUD is still in-memory (module-level dict); only /api/v1/scenes/persist is durable.
  • B9 — ~22 GB free; Zenodo archives (96 GB) cannot be staged here.

9.3 Technical debt (code-level)

  • Shared core is dead weight. sentinel_core is not imported by any service; config + loguru are re-implemented per service. The training harness uses it, but services don't — so two config truths can drift apart.
  • Port drift. detect/app/main.py hardcodes port=8000 (same as the gateway) while compose runs it on 8002; the gateway's DETECT_SERVICE_URL default matches the deploy wiring, not the in-code default.
  • Two entry points per detection/drift service (main vs main_det / main_attribution) — a real maintenance fork that must be selected correctly per environment.
  • AOIs as strings. A west,south,east,north lat-first string is four numbers legal in either slot; a lat/lon swap is invisible to any validator. Code now prefers named axes (min_lon…).
  • Manifest defines the dataset, not the listing. The scene_leakage guard was vacuous twice over (ids collapsed to the archive dir; loader ignored the manifest's scene_id). Now fixed, but it shows a guard that can't fail is not a guard.
  • Untracked real data. data/sar/ (6 COG GeoTIFFs) is gitignored; 5 tests skip without it. Demo product ID in the original brief does not exist.

10 · Where It Excels vs. Where a Different Approach Fits

Excels when…

  • Reproducibility and auditability matter more than peak accuracy. Explainable deterministic detection + full provenance + stated CIs is ideal for a legal/regulatory evidence package (IMO MEPC referral).
  • Data is sensitive or immovable. Reading the real archive in place with a SHA-256 proof is exactly right for read-only external disks / constrained environments.
  • You need to measure leakage and selection bias rather than hope it isn't there. The footprint grouping + held-out test + atomic reporting is a model-evaluation template worth copying.
  • Honest uncertainty communication to analysts who will act on the output (every datum shows confidence).

Struggles / a different approach is better when…

  • You need a deployed, accurate detector. No trained model ships; if detection accuracy is the product, train and benchmark a proper segmentation model on a labelled set (Zenodo + held-out Part III) first — that is the single highest-value gap.
  • You need real vessel attribution. Without a satellite-AIS subscription the attribution stage returns empty. A different data source (paid historical AIS) is a prerequisite, not an architecture fix.
  • You need calibrated probabilities. The Wilson CI is evidence-consistency, not P(oil). For risk scoring you need a labelled benchmark to calibrate against.
  • You are operating at scale with many concurrent scenes. A microservice mesh on one 16 GB laptop with no GPU is fragile; the full compose is unbuilt and the lite profile drops Prometheus/Grafana/worker/intel. A single merged service or a GPU box would simplify operations.
  • Wind/ocean forcing is unavailable. Look-alike discrimination collapses without a 2–10 m/s wind field; a purely SAR pipeline will misclassify low-wind patches.
  • Maintainability of two entry points + duplicated config is a drag — consolidate detection into one configurable app and wire sentinel_core into the services to remove the dual-config debt.
Suggested next steps, in value order (from the project handover):
  1. Get more acquisitions into val/test (8 and 6 is why the held-out estimate is wide).
  2. Attack the over-prediction: threshold selection + augmentation that varies acquisition conditions (incidence angle, wind), not just geometry.
  3. Build Dockerfile.train once on a machine with a daemon.
  4. Verify the SAR band order against a declared-acquisition source to close B12.
